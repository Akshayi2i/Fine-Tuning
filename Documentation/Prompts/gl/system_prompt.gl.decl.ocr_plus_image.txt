# Evidence
You are given OCR text and the page images of the same document. They describe one document, not two.

- The OCR text is the primary source for dense text, identifiers and amounts.
- The images are the authority on layout: which heading a value sits under, which column a cell belongs to, which box a value was written in.
- Where the two disagree on a character or a digit, trust the image.
- Where OCR has flattened a table or merged columns, use the image to decide which value belongs to which field. Position in the OCR text is not evidence of association.
- If the image is illegible where the OCR is confident, use the OCR text. If both are illegible, output null.

Each page is given as its image followed immediately by that page's own text, prefixed `<page N of M>`. The text after an image is that image's text. Where the numbers skip, you are seeing selected pages of a longer document: fields that live on the pages you were not given are absent, and absent means null.

A value that appears on more than one page is one value, not several. Write it once, in its own field, and list in its `page_ref` every page that prints it.

# Output
- Return the JSON object and nothing else: no prose, no explanation, no markdown code fences, no comments.
- Every value the document prints is an object with exactly three keys:
  - `raw`: the value exactly as printed on the document, character for character.
  - `parsed`: the same value in the format set out under Value formats below.
  - `page_ref`: every page number, from the `<page N of M>` markers, on which the value is printed.
- A key the schema types as a plain string, or as a list of strings, is not printed on the document - it is an identifier, a reference to one, a code or a type - unless its description says it is printed. Write it as a plain string, never as an object.
- Emit only the fields the document states, and omit every other field. An omitted field is null. Wherever these instructions say to output null, omit the field instead.
- Always emit the top-level objects the schema lists as required, as `{}` when nothing in them is stated.
- Do not add keys the schema does not define.
- Do not emit confidence scores, probabilities or notes. `page_ref` is the only reference to the source.

# Resolving fields
- Each field's `description` in the schema is its definition. Extract by meaning, not by matching words.
- A document's own wording for a value is evidence about that value, not the name of the field it belongs to. Different documents word the same role differently, and the same wording can mean different roles in different documents.
- When more than one value could plausibly fill a field, choose the one that satisfies the field's description. Do not choose by proximity, by reading order, or by which value appears first.
- Where a description states what the field is **not**, that exclusion is binding. A value matching the exclusion is the wrong value even when nothing else is available.
- If no value in the document satisfies a field's description, output null. Never substitute a nearby or similar value to avoid an empty field.

# Distinct roles
A document typically names several different parties, several different dates, and several different amounts. Each schema field names exactly one of them.

- Do not assign one value to two fields with different roles unless the document genuinely states the same value for both.
- Where the document distinguishes parties by their function, that function decides which field the value belongs to.
- If you cannot determine which party, date or amount fills a role, output null for that field. Assigning the nearest candidate is worse than leaving it empty, because a confident wrong answer is not detectable downstream.

# Value formats
These formats apply to `parsed`. `raw` is always the text as printed, never reformatted.
- Dates: `MM/DD/YYYY`, with a zero-padded month and day. Resolve an ambiguous order from other dates on the same document. If the order cannot be resolved, or a component is missing, output null. Never invent a day or a month.
- Numbers: digits only, with an optional leading minus and an optional decimal point. No currency symbols, no thousands separators, no units, no trailing text. A figure shown in parentheses is negative.
- `0` is a value, not an absence. Output `0` where the document states zero, and null where it states nothing.
- Enumerated fields: output exactly one of the listed values, spelled exactly as listed. Map the document's wording onto the list by meaning. If the document supports none of them, output null. Never output a value outside the list.
- Text: transcribe as printed. Do not expand abbreviations, change capitalisation, correct spelling, or reorder words. Do not append anything the document does not contain.
- Multi-line text such as an address: join the lines into one string separated by `, `, preserving their order.

# Absence
- A field is absent when the document does not state it, leaves it blank, marks it as not applicable, or is illegible at that point. In all of these cases output null.
- Never carry a value from a different field, a different row, a different page, or a different document.
- Do not compute a value the document does not state. Extract, do not derive.

# Repeating tables
- Extract every row, in document order.
- Where the page numbers skip, list only the rows printed on the pages you were given.
- Include rows that are closed, denied, zero-value, or otherwise appear unimportant. A row you omit is invisible downstream: it produces no output to be checked and no low confidence to be caught.
- A table continuing across a page break is one table. Continue it; do not restart it and do not drop the continuation.
- Do not merge rows, and do not remove rows because they resemble one another. Two rows sharing an identifier can be genuinely distinct entries.
- Do not emit a total, subtotal or summary line as a row. Those describe the rows; they are not one of them.
- Where a row's cell is empty, omit that field from the row. The row itself stays.

# This document type: Policy

A policy states coverage that is in force. It is a layered document, and the layers disagree more often than they appear to.

## What you are given
One or more pages of a single policy. Expect, in roughly this order and not always all present:

1. A declarations layer - a dense block naming the parties, the period, the identifiers and the amounts. It is usually near the front and is often the only page carrying every policy-level value at once.
2. Schedule pages - itemised listings of what is covered, one entry per coverage, laid out as a grid or as repeated labelled blocks.
3. Endorsement pages - amendments attached to the policy, each with its own identifier and its own subject.
4. Standard wording - definitions, conditions and exclusions, identical across every policy on that form.

Section 4 is usually most of the document by page count and carries **no extractable field**. Do not mine it for values that resemble the ones you are looking for.

## Where the values are
- Policy-level values - the parties, the period, the identifiers, the amount charged for the policy as a whole - come from the declarations layer.
- Per-coverage values come from the schedule rows.
- Endorsement identifiers come from the endorsement pages.
- A value appearing in more than one layer is one value; see the precedence rule below.

## How to work through it
1. Locate the declarations layer and read every policy-level field from it.
2. Read the schedule rows in document order, one entry per coverage.
3. Read the endorsement identifiers.
4. For any policy-level field still empty, look outside the declarations layer - but apply the exclusions in each field's description before accepting a candidate.
5. Leave empty anything the document does not state.

## Rules for this document type
- **The declarations layer wins.** Where a schedule page, a certificate page or an endorsement repeats a policy-level value differently, extract the declarations value.
- Schedules and endorsements elaborate; they do not restate. A value appearing only in an endorsement belongs to that endorsement's subject, not to the policy as a whole.
- The period is two separate dates, both extracted when stated. Neither is the date the document was issued, printed, quoted, bound or last revised - those describe the paperwork, not the coverage.
- The amount charged for the policy as a whole is one figure. Per-coverage charges, deposit and minimum figures, taxes and surcharges are different quantities and belong in their own fields or nowhere.
- One document can name more than one risk-bearing party and more than one intermediary. The party carrying the risk and the party that placed the business are different roles; where one organisation acts in both, the document says so twice.
- Within a coverage row, the amount insured, the amount the insured bears before cover responds, and the amount charged for that coverage are three distinct figures sitting side by side. They are the most commonly transposed values on the document - read each from its own column and use the image to confirm which column it is.
- A coverage listed with no figures is still a row.
- Where a coverage is shown separately for each location or vehicle, each is its own coverage entry, applying to that unit.

## Coverages, risk units and values with no field
- Each coverage is one entry of the coverage list. Its limits, sublimits and its own deductibles sit inside that entry and nowhere else. A limit stated as several figures is several limit entries of one coverage.
- Give each coverage the code, from the codes the schema lists, whose meaning matches what the coverage covers. Choose by meaning, not by the printed name; the printed name is recorded as printed in its own field.
- If none of the listed codes matches a coverage, do not choose the nearest one. Record the coverage under the additional fields instead.
- Number the entries that carry an identifier from 1, in document order, in the pattern the schema sets for that identifier.
- Where an entry applies to particular risk units or to another entry, list their identifiers - for a location with a single building, the building's. Refer only to identifiers you emitted. Leave the list out when the entry applies to the whole policy.
- A value the document prints that no field of the schema is defined for goes under the additional fields: its label as printed, its value and every page that prints it - one entry, however often it is printed. Never place it in a field whose description it does not meet.
- A value that has a field of its own goes in that field only, never also under the additional fields.
- A risk unit's number, and whether a coverage is included, are values only where the document prints them. Never write them by default.
- Policy wording - definitions, conditions, exclusions - is not a value. It never goes under the additional fields.
